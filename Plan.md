# Kanban — план проєкту

Оновлено: 2026-10-28. Поточний етап: **A0 — підготовка**.

**Команда:** власник проєкту розробляє backend; друг — frontend. API, поведінку продукту та інтеграцію погоджуємо разом.

**Стратегія:** спочатку завершений модульний моноліт із живим демо, потім — окремий етап поступової міграції на мікросервіси. Перший самостійний результат — `v1.0-monolith`.

Цей документ є робочим орієнтиром для подальшої розробки. Чекбокси позначаємо лише після реалізації та перевірки. Поточний результат: API-draft, backend-каркас, PostgreSQL, auth-сутності й репозиторії, Flyway, DTO та проста обробка помилок. Є Spring Security, BCrypt, RS256 JWT, CSRF, реєстрація, логін, `/users/me`, refresh та `POST /api/v1/auth/logout`. Logout відкликає поточну refresh-сесію, очищає обидві cookie та повертає `204`; повторний вихід безпечний. Реалізовано очищення завершених сесій через 7 днів (щогодини, до 500 за запуск) та локальний rate limit register/login/refresh з `429` і `Retry-After`. Повний Maven `clean verify`: 160 тестів без помилок і пропусків. Браузерна інтеграція, CI та інший бізнес-функціонал ще попереду.

## 1. Мета та пріоритети

Створити Kanban-дошку для власного використання і портфоліо: користувачі керують завданнями та спільно працюють над дошками.

Пріоритети за порядком:

1. Робочий наскрізний сценарій: реєстрація → дошка → колонки → картки → переміщення.
2. Коректність даних, перевірка доступу та зрозуміла поведінка при помилках.
3. Спільна робота, історія змін і realtime.
4. Відтворюваний запуск, тести, документація та публічне демо.
5. Міграція на мікросервіси як окреме інженерне завдання після завершення моноліту.

## 2. Межі першої версії

### Проміжна версія `v0.1-core`

- Реєстрація, вхід, оновлення токенів і вихід.
- Список власних дошок; створення, редагування та видалення дошки.
- Створення, редагування, видалення та впорядкування колонок.
- Створення, редагування та видалення карток; назва й опис картки.
- Перетягування карток у межах колонки та між колонками.
- Дошки приватні; доступ має лише власник. Перевірки власника працюють з першого CRUD.
- Ранній тестовий деплой і можливість перевірити весь сценарій через браузер.

### Реліз `v1.0-monolith`

До ядра додаються:

- Учасники дошки та ролі `OWNER`, `EDITOR`, `VIEWER`.
- Запрошення посиланням: строк дії, одноразове прийняття та можливість відкликання. Для прийняття потрібен обліковий запис. Автоматичне надсилання email відкладаємо.
- Один виконавець картки з-поміж учасників дошки.
- Коментарі: створення та видалення власних; власник дошки може модерувати коментарі.
- Історія змін із пагінацією.
- Realtime-оновлення відкритої дошки та toast-сповіщення про релевантні зміни.
- Відновлення актуального стану після втрати з'єднання.
- Обробка помилок, порожніх станів і завантаження; базова адаптивність та доступність.
- HTTPS, резервне копіювання, моніторинг, README та живе демо.

### Після `v1.0`, за пріоритетом

Лейбли, дедлайни, фільтри й пошук, темна тема, архівування, кілька виконавців, email-сповіщення, центр сповіщень, online-присутність.

На початкових етапах не додаємо Kafka, gateway, Kubernetes, вкладення, OAuth, організації та складні робочі процеси. Нові функції включаємо до поточного релізу лише з явним переглядом його обсягу.

## 5. Архітектура модульного моноліту

```text
React + TypeScript
       │ REST /api/v1 + STOMP /ws
       ▼
Nginx: frontend + проксі до backend
       │
       ▼
Spring Boot
  auth │ board │ activity │ notification
       │            │
       └─────┬──────┘
             ▼
PostgreSQL: окрема схема на модуль
            + технічні таблиці журналу подій

Redis — за потреби; Kafka та gateway — на етапі B.
```

### Межі модулів

| Модуль | Володіє даними та поведінкою |
|---|---|
| `auth` | Користувачі, парольні хеші, refresh-сесії, видача токенів, мінімальний профіль |
| `board` | Дошки, колонки, картки, учасники, ролі, запрошення, коментарі, перевірки доступу до дошки |
| `activity` | Історія дій, обробка доменних подій, читання історії |
| `notification` | Realtime-доставка, підписки й обробка подій; згодом email |

Правила реалізації:

1. Один застосунок і одна збірка backend. Модулі спочатку є пакетами, а не окремими сервісами.
2. У кожного модуля є вузький API та внутрішні пакети. Якщо API винесено в підпакет `api`, позначаємо його як named interface Spring Modulith.
3. Чужі JPA-сутності, репозиторії та внутрішні сервіси не імпортуємо. `public` для взаємодії підпакетів одного модуля допустимий; зовнішній доступ обмежує архітектурний тест.
4. Дозволені залежності задаємо явно; циклів між модулями немає. `auth` не залежить від `board`; `activity` та `notification` можуть використовувати API `board` для перевірки доступу.
5. Події дошки належать API модуля `board`. Ядро дошки не викликає модулі історії та сповіщень напряму.
6. Бізнес-сутності не перетворюємо на спільну модель у `common`. Спільний код обмежуємо невеликими технічними утилітами.
7. Схеми `auth`, `board`, `activity`, `notification` мають власників-модулів. Немає міжмодульних SQL JOIN, foreign key та JPA-зв'язків; посилання між модулями — UUID.
8. Усередині схеми використовуємо foreign key, unique/check constraints та індекси за потребою. Відсутність зв'язків між схемами не скасовує перевірку бізнес-правил через API модулів.
9. Flyway запускається централізовано: міграції мають унікальні версії, SQL явно задає схему. Міграції технічного журналу подій також контролюються.
10. Залежності перевіряє `ApplicationModules.of(Application.class).verify()` у CI. Додаткові правила ArchUnit вводимо для конкретних обмежень, яких ця перевірка не покриває.

Підстава для правил модульності: [Spring Modulith — Fundamentals](https://docs.spring.io/spring-modulith/reference/fundamentals.html) і [Verification](https://docs.spring.io/spring-modulith/reference/verification.html).

## 6. Дані, доступ і конкурентні зміни

### Основні сутності

| Схема | Сутності |
|---|---|
| `auth` | `User`, `RefreshSession` |
| `board` | `Board`, `BoardMember`, `BoardInvitation`, `BoardColumn`, `Card`, `Comment` |
| `activity` | `ActivityEntry`, облік оброблених подій |
| `notification` | Облік обробки та доставки подій; згодом збережені сповіщення |

Ідентифікатори — UUID. Час зберігаємо як UTC (`timestamptz`), у UI показуємо локально. Для списків зростаючого розміру використовуємо пагінацію та стабільне сортування.

### Права на дошці

| Дія | OWNER | EDITOR | VIEWER |
|---|---|---|---|
| Читати дошку, коментарі та історію; отримувати realtime | Так | Так | Так |
| Змінювати колонки, картки та виконавців | Так | Так | Ні |
| Додавати коментарі, видаляти власні | Так | Так | Ні |
| Модерувати чужі коментарі | Так | Ні | Ні |
| Змінювати налаштування дошки, запрошувати, керувати ролями | Так | Ні | Ні |
| Видаляти дошку | Так | Ні | Ні |

- Рівно один власник; передачу власності можна додати пізніше. Видалення власника як звичайного учасника заборонене.
- Картка належить колонці тієї самої дошки; переміщення між різними дошками не входить у `v1.0`.
- Виконавцем може бути лише учасник дошки. При вилученні учасника його призначення на цій дошці знімаються.
- Колонку з картками не видаляємо мовчки: повертаємо конфлікт і пропонуємо спочатку перемістити або видалити картки.
- Кожен endpoint перевіряє доступ до відповідного ресурсу. Приховування кнопок у UI не замінює серверну перевірку.

### Порядок карток і колонок

- Використовуємо fractional indexing на PostgreSQL `NUMERIC`, а не `double`. Початкову точність фіксуємо в ER-діаграмі.
- Сервер обчислює позицію між сусідами; клієнт передає цільову колонку та ідентифікатори сусідів.
- Якщо проміжок вичерпано, сервер перенумеровує відповідний список у транзакції.
- У першій версії операції зміни порядку серіалізуємо коротким блокуванням рядка дошки. Створення елементів у впорядкованому списку використовує той самий механізм.
- Для конкурентного редагування використовуємо версію сутності (`@Version`); очікувану версію передаємо в запиті.
- Застаріле редагування повертає `409 Conflict`; UI оновлює дані та пояснює конфлікт користувачеві.
- Окремо перевіряємо одночасні переміщення, видалення сусіда та переміщення до порожньої колонки.

## 7. Контракт backend ↔ frontend

Початкова пропозиція для A0–A1: [OpenAPI](docs/api/openapi.yaml) і [пояснення з прикладами](docs/api/README.md). Статус — draft для спільного погодження; реалізація та ER-діаграма ще попереду.

- HTTP API має префікс `/api/v1`; сутності БД назовні не повертаємо, використовуємо DTO.
- Джерело контракту — `docs/api/openapi.yaml`. Перед реалізацією вертикальної задачі узгоджуємо маршрути, DTO, статуси, помилки та приклади.
- Frontend генерує клієнт через orval і працює з MSW до готовності endpoint. Згенеровані файли не редагуємо вручну.
- Backend використовує springdoc для документації та перевірки відповідності реалізації узгодженій специфікації. Розбіжності виправляємо до завершення задачі.
- Описуємо required/nullable поля, обмеження довжини, UUID, дати, пагінацію, сортування та запити переміщення.
- Помилки — прості JSON DTO зі `status`, `error`, стабільним `code`, `message` і `timestamp`; для валідації request body замість `message` повертаємо `errors` як об'єкт «поле → повідомлення».
- Фіксуємо поведінку для `400`, `401`, `403`/`404`, `409` та `429`. Для приватних ресурсів узгоджуємо політику `404`, щоб не розкривати чужі дошки.
- Несумісні зміни погоджуємо до зміни коду та одночасно оновлюємо специфікацію, приклади й моки.
- Під час міграції зберігаємо публічні URL, HTTP- та WebSocket-контракти; змінюється внутрішня маршрутизація.

Серверні дані на frontend зберігає TanStack Query. Локальний стан форми, модалки чи перетягування не дублює всю дошку в окремому глобальному сховищі. Optimistic UI має відкат при помилці та повторне отримання актуального стану.

## 8. Події та realtime

### Надійність у моноліті

- Формат подій проєктуємо в A0; надійний механізм підключаємо разом із першими подіями, до реалізації залежних функцій.
- Базовий вибір — JDBC Event Publication Registry Spring Modulith: запис про публікацію зберігається в тій самій транзакції, що й бізнес-зміна. Налаштовуємо повторну обробку незавершених публікацій.
- Не додаємо паралельно власний outbox з тією самою відповідальністю. Якщо можливостей registry не вистачить, заміну або окремий інтеграційний outbox описуємо в ADR.
- Звичайний асинхронний Spring listener без стійкого журналу не вважаємо гарантією доставки.
- Доставка допускає повтори. Обробники ідемпотентні; запис ефекту та позначка обробки виконуються в одній транзакції, де це можливо.
- Помилка історії або сповіщення після коміту не скасовує вже збережену картку. Відновлення обробки перевіряємо тестом із перезапуском.

Цей вибір спирається на [Spring Modulith — Working with Application Events](https://docs.spring.io/spring-modulith/reference/events.html).

### Контракт події

Мінімальний envelope: `eventId`, `type`, `schemaVersion`, `occurredAt`, `actorId`, `aggregateId`, `aggregateVersion`, `payload`; для подій дошки також обов'язковий `boardId`.

Початкові типи: `BoardCreated`, `BoardUpdated`, `BoardDeleted`, `ColumnCreated`, `ColumnUpdated`, `ColumnMoved`, `ColumnDeleted`, `CardCreated`, `CardUpdated`, `CardMoved`, `CardDeleted`, `MemberAdded`, `MemberRemoved`, `MemberRoleChanged`, `CommentAdded`, `CommentDeleted`.

Точний набір і payload описуємо з відповідною функцією. Події не містять парольних хешів, токенів та зайвих персональних даних. Внутрішня подія й публічне WebSocket-повідомлення мають окремі DTO.

### Поведінка WebSocket

- HTTP залишається основним способом виконання команд; STOMP повідомляє про збережені зміни.
- Автентифікацію через STOMP `CONNECT` із access-токеном та прив'язку `Principal` реалізуємо й документуємо явно. Токени не передаємо в URL.
- Підписка `/topic/boards/{boardId}` потребує перевірки членства. Клієнт не може публікувати довільні повідомлення до серверних topic.
- Відкликання доступу припиняє активні підписки відповідного користувача на дошку. Закінчення токена обробляємо через контрольоване перепідключення.
- У `v1.0` подія переважно інвалідує потрібні запити TanStack Query. Складне застосування дельт додаємо лише за потреби.
- Після reconnect завжди отримуємо поточний стан через REST: WebSocket не є журналом для гарантованого відтворення пропущених подій.
- Повтори подій не створюють повторних записів історії чи toast; optimistic UI узгоджується з серверним станом.
- Недоступність WebSocket показуємо в UI; користувач зберігає можливість працювати через REST.

Правила авторизації повідомлень і підписок враховують [Spring Security — WebSocket Security](https://docs.spring.io/spring-security/reference/servlet/integrations/websocket.html).

## 9. Безпека та інфраструктура

### Авторизація й сесії

- Паролі хешуємо BCrypt. Access JWT короткоживучий; початковий орієнтир — 15 хвилин.
- Refresh-токен — випадковий секрет; на сервері зберігаємо його хеш, строк дії та стан сесії в PostgreSQL.
- Реалізуємо ротацію refresh-токенів, вихід і відкликання сесії; поведінку повторного використання описуємо в контракті.
- На frontend access-токен тримаємо в пам'яті, refresh — у `HttpOnly`, `Secure` cookie з узгодженим `SameSite` і шляхом. Cookie-потоки мають захист від CSRF.
- Для production frontend і API працюють під одним origin. Локальний Vite proxy відтворює цей спосіб взаємодії.
- Обмеження частоти входу та реєстрації додаємо на початку. Для одного інстансу можливий локальний limiter; для кількох потрібне спільне сховище.
- Секрети не комітимо: `.env.example` містить лише приклади, production використовує секрети середовища та GitHub Secrets.

### Запуск і доставка

- На A0 Compose запускає PostgreSQL; backend і frontend можна запускати з IDE. Redis і моніторинг підключаємо окремими профілями, коли вони потрібні.
- До релізу весь застосунок запускається документованою командою Compose; потрібні змінні описані в README.
- CI на PR: backend build і тести, межі модулів, frontend lint/typecheck/build, перевірка контракту та інтеграційні тести відповідних функцій.
- Docker-образи публікуємо в GHCR із тегом commit SHA. Автодеплой після merge в `main` вмикаємо після перевірки ручного деплою й відкату.
- Production: VPS, Docker Compose, Nginx, HTTPS, persistent volumes, health/readiness checks і контрольований запуск міграцій.
- Резервні копії PostgreSQL зберігаємо поза сервером; до `v1.0` перевіряємо відновлення на тестовому середовищі.
- Схему БД змінюємо сумісно з відкатом застосунку. Деструктивні зміни й перенесення даних плануємо окремо.

### Спостереження та кеш

- Структуровані логи з `traceId`; без паролів, токенів та зайвого вмісту користувацьких даних.
- До релізу: метрики HTTP-затримок і помилок, пулу БД, незавершених подій та WebSocket-з'єднань; базовий дашборд і перевірка доступності.
- Actuator і метрики не відкриваємо публічно без обмеження доступу.
- Кеш дошки додаємо після вимірювання запитів і затримок. Якщо він потрібен, визначаємо ключі, TTL, інвалідацію та поведінку при відмові Redis.
- Перевірки доступу не залежать від застарілого кешу; realtime-доставка в одному інстансі не потребує Redis pub/sub.

## 11. Критерії готовності та перевірки

### Для кожної задачі

- [ ] Погоджена поведінка реалізована; перевірено помилки й доступ, якщо задача їх зачіпає.
- [ ] Контракт, моки та документація актуальні, якщо поведінка API змінилася.
- [ ] Є доречні перевірки: бізнес-правила та інтеграції покриті тестами; для невеликої косметичної зміни достатньо візуальної перевірки.
- [ ] Зміни схеми мають Flyway-міграцію; секрети й випадкові локальні файли відсутні в diff.
- [ ] CI проходить; інтегрований сценарій перевірено до позначення задачі завершеною.

### Перед `v1.0-monolith`

- [ ] Повний сценарій: реєстрація → дошка → запрошення → картка → виконавець → коментар → переміщення → історія/realtime.
- [ ] `VIEWER` не змінює дані; сторонній користувач не читає дошку та не підписується на її події.
- [ ] Невалідні токени, прострочені запрошення й застарілі версії редагування обробляються передбачувано.
- [ ] Одночасні переміщення не гублять картки та не руйнують порядок.
- [ ] Повторна подія не дублює історію; незавершена обробка відновлюється після рестарту.
- [ ] Після reconnect дошка синхронізується, а вилучений учасник припиняє отримувати дані.
- [ ] Застосунок запускається за README; production-дані переживають перезапуск.
- [ ] Резервна копія відновлена на тестовій БД; процедура відкату задокументована.
- [ ] Є демо, архітектурна схема й результати базового навантажувального тесту без неперевірених обіцянок продуктивності.

Інтеграційні тести додаємо під час відповідного етапу, а не відкладаємо до релізу. Для SQL, міграцій і транзакцій використовуємо реальний PostgreSQL через Testcontainers.

## 12. Етап B — поступова міграція на мікросервіси

**Умова початку:** `v1.0-monolith` завершений і задеплоєний; окремо погоджено перехід до етапу B. До цього моменту його задачі не входять у поточну реалізацію.

Мета міграції — навчитися розділяти працюючу систему, зберегти поведінку та виміряти наслідки. Прискорення або спрощення від самого поділу не припускаємо.

### B0. Підготовка — орієнтир 1 тиждень

- [ ] Зафіксувати ADR: причина міграції, залежності модулів, порядок виділення та план відкату.
- [ ] Додати Spring Cloud Gateway перед монолітом зі збереженням `/api/v1` і WebSocket-маршрутів.
- [ ] Додати Kafka KRaft та перевірений міст із наявного журналу подій. Зміна транспорту не має створити пропусків або неконтрольованої подвійної обробки.
- [ ] Визначити topics, ключі, версії контрактів, retries, DLT та метрики відставання.
- [ ] Для пов'язаних подій дошки початковий кандидат — один `board.events` із ключем `boardId`; для подій користувача — `user.events` із ключем `userId`.
- [ ] Документувати порядок: Kafka впорядковує записи в межах партиції; ключ не створює загального порядку між різними topics і не виправляє порушення порядку в relay або retry.

Ці обмеження доставки враховують [Apache Kafka — Design](https://kafka.apache.org/41/design/design/).

### B1. Виділення сервісів — орієнтир 3–4 тижні, уточнюється після ADR

Попередній порядок: `activity` → `notification` → `auth`; залишок моноліту стає `board-service`. Починаємо з історії як споживача подій. Перед виділенням кожного модуля окремо розв'язуємо його залежності, зокрема перевірку членства в дошці. Realtime потребує додаткової уваги до авторизації підписок і відкликання прав.

Для кожного сервісу:

- [ ] Визначити його HTTP- та event-контракти, джерело перевірки доступу та поведінку при недоступності залежностей.
- [ ] Підготувати окремий застосунок, БД, конфігурацію, CI й образ.
- [ ] Перенести дані зі збереженням ідентифікаторів, перевіркою повноти та планом переходу/відкату.
- [ ] Переключити consumer і маршрути, виключивши небажані подвійні ефекти.
- [ ] Пройти контрактні та інтеграційні тести, задеплоїти, перевірити метрики.
- [ ] Прибрати старий модуль лише після підтвердження роботи нового сервісу.

Gateway перевіряє токен, але бізнес-права на дошці продовжує перевіряти сервіс, що виконує операцію. Redis pub/sub для realtime додаємо, коли є кілька інстансів; він не замінює надійний журнал подій.

### B2. Завершення — орієнтир 1–2 тижні

- [ ] Додати розподілене трасування OpenTelemetry та дашборди сервісів.
- [ ] Повторити навантажувальні сценарії на зіставному середовищі; описати затримки, помилки й витрати ресурсів порівняно з монолітом.
- [ ] Оновити Compose, інструкції деплою, відновлення та архітектурну схему «до/після».
- [ ] Задокументувати компроміси й результати міграції, створити `v2.0-microservices`.

Kubernetes/k3s розглядаємо після міграції як окреме завдання за наявності потреби.
