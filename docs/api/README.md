# Контракт backend ↔ frontend: v0.1-core

**Статус: draft; реалізовано Spring Security, `GET /auth/csrf`, `POST /auth/register`, `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout` і `GET /users/me`; endpoint дошок ще попереду.** Версія специфікації: `0.1.0-draft.2`. Rate limit (`429`) реалізовано; браузерна інтеграція ще не завершена.

Машиночитане джерело — [openapi.yaml](./openapi.yaml). Цей документ пояснює домовленості та приклади. Контракт покриває A0–A1 з `Plan.md`: авторизацію, приватні дошки, колонки, картки та переміщення. Учасників, коментарі й realtime додаємо на відповідних етапах.

## 1. Загальні домовленості

- Базовий шлях: `/api/v1`. У production frontend і backend мають один origin; локально frontend звертається через Vite proxy.
- Запити й успішні відповіді — JSON з `camelCase`. `204 No Content` не має тіла, його не потрібно парсити як JSON.
- Ідентифікатори — UUID-рядки; час — ISO 8601 у UTC, наприклад `2026-10-22T09:00:00Z`.
- У відповідях порожні списки — `[]`, порожній опис — `""`. Ці поля не повертаються як `null`.
- У PATCH відсутнє поле означає «не змінювати», `description: ""` означає «очистити». `null` заборонений, крім явно nullable ID сусідів у move.
- Невідомі поля request body відхиляються. Frontend допускає додаткові поля у відповідях, щоб сумісні розширення не ламали клієнт.
- `title`: 1–200 символів після обрізання пробілів із країв. `description`: до 10 000 символів, звичайний текст. Для лімітів рахуємо Unicode code points; UTF-16 `string.length` не завжди дає ту саму кількість.
- Email нормалізується через trim і lowercase. Новий пароль при реєстрації: 12–72 символи; при вході потрібен непорожній пароль без повторної перевірки мінімальної довжини. В обох випадках пароль не обрізаємо й не нормалізуємо, ліміт BCrypt — 72 UTF-8 байти. Для frontend байтову довжину дає `new TextEncoder().encode(password).length`.
- Звичайні успішні відповіді не загортаємо в `{ data: ... }`. Для списку дошок є окремий об'єкт пагінації.
- Персональні відповіді та auth-відповіді мають `Cache-Control: no-store`; кеш frontend керується TanStack Query.
- У core роль завжди `OWNER`; `EDITOR` і `VIEWER` зарезервовані в DTO для A2, самі права цих ролей ще не реалізовані.

## 2. Авторизація

| Метод | Шлях | Результат |
|---|---|---|
| GET | `/auth/csrf` | `200`: CSRF-токен і відповідна cookie |
| POST | `/auth/register` | `201`: користувач, access-токен і refresh cookie |
| POST | `/auth/login` | `200`: користувач, access-токен і refresh cookie |
| POST | `/auth/refresh` | `200`: нові access-токен і refresh cookie |
| POST | `/auth/logout` | `204`: поточна refresh-сесія відкликана, cookie видалена |
| GET | `/users/me` | `200`: профіль поточного користувача |

Access-токен передається як `Authorization: Bearer <accessToken>` і зберігається лише в пам'яті frontend. Refresh-токен не передається в JSON, localStorage чи URL. Його встановлює backend у `kanban_refresh`: `HttpOnly; Secure; SameSite=Lax; Path=/api/v1/auth`, без `Domain`. Початковий TTL access — 900 секунд; refresh-сесії — 7 днів від останньої успішної ротації. Це запропоновані налаштування, які фіксуємо перед реалізацією.

У локальному профілі з HTTP допускається cookie без `Secure`; production завжди HTTPS із `Secure`. Це явна конфігурація середовища, а не залежність від поведінки конкретного браузера.

Для всіх auth-запитів використовуємо `credentials: "include"`. Перед auth POST викликаємо `GET /auth/csrf`, отримуємо `{ "token": "...", "headerName": "X-CSRF-TOKEN" }` і передаємо токен у відповідному заголовку. Сервер звіряє його з CSRF cookie. Після register/login/logout отримуємо CSRF-токен повторно; налаштування Spring Security має підтримувати цей SPA-потік. Команди до дошок використовують лише Bearer, без автентифікації через cookie.

Register, login і refresh мають локальний rate limit до операцій BCrypt і БД, після CSRF і валідації DTO. Типові ліміти: register — 5/IP за годину, login — 30/IP і 10/нормалізований email за 15 хвилин, refresh — 120/IP за хвилину. Успішні й невдалі спроби рахуються однаково; пороги налаштовуються. При `429 RATE_LIMITED` зачекати `Retry-After` секунд: cookie залишаються чинними й refresh не змінюється. Logout не обмежується цими лічильниками. Ліміти діють у межах одного процесу й скидаються при рестарті; подробиці конфігурації — у [backend README](../../backend/README.md).

Приклад реєстрації:

```http
POST /api/v1/auth/register
Content-Type: application/json
X-CSRF-TOKEN: <csrfToken>
```

```json
{
  "email": "developer@example.com",
  "password": "example-password-123",
  "displayName": "Олексій"
}
```

Відповідь `201` (`accessToken` нижче — умовний приклад; у реалізації це валідний JWT):

```json
{
  "accessToken": "<access-jwt>",
  "tokenType": "Bearer",
  "expiresIn": 900,
  "user": {
    "id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
    "email": "developer@example.com",
    "displayName": "Олексій",
    "createdAt": "2026-10-22T09:00:00Z"
  }
}
```

Поведінка frontend:

1. Після перезавантаження сторінки: отримати CSRF → спробувати refresh → відновити користувача з відповіді або показати форму входу після `401`.
2. Якщо захищений запит отримав `401`, виконати один refresh і повторити початковий запит не більше одного разу. Сервер відхиляє неавтентифікований запит до виконання бізнес-операції.
3. Одночасні запити мають очікувати один refresh. Кілька вкладок теж координують ротацію, щоб не використати один refresh двічі; це окрема задача frontend.
4. `401` від refresh означає завершення сесії. `403 CSRF_INVALID` означає необхідність отримати новий CSRF, а не запускати цикл refresh. При `5xx` або мережевій помилці показуємо тимчасовий збій, а не оголошуємо сесію недійсною.
5. Logout відкликає поточну refresh-сесію; вже виданий JWT може діяти до завершення його короткого TTL. Вихід на всіх пристроях не входить у core.
6. Автоматично не повторюємо створення чи move після невідомого результату через мережевий збій: спочатку оновлюємо стан, щоб уникнути дублювання.

## 3. Дошки, колонки й картки

У таблиці всі шляхи мають префікс `/api/v1` і потребують Bearer-токена.

| Метод | Шлях | Призначення | Успіх |
|---|---|---|---|
| GET | `/boards?page=0&size=20` | Список власних дошок | `200` |
| POST | `/boards` | Створити дошку | `201` |
| GET | `/boards/{boardId}` | Вся дошка з колонками й картками | `200` |
| PATCH | `/boards/{boardId}` | Змінити назву/опис | `200` |
| DELETE | `/boards/{boardId}?version=0` | Видалити дошку з її вмістом | `204` |
| POST | `/boards/{boardId}/columns` | Додати колонку в кінець | `201` |
| PATCH | `/boards/{boardId}/columns/{columnId}` | Перейменувати колонку | `200` |
| DELETE | `/boards/{boardId}/columns/{columnId}?version=0` | Видалити порожню колонку | `204` |
| POST | `/boards/{boardId}/columns/{columnId}/move` | Перемістити колонку | `200` |
| POST | `/boards/{boardId}/columns/{columnId}/cards` | Додати картку в кінець | `201` |
| GET | `/boards/{boardId}/cards/{cardId}` | Отримати картку | `200` |
| PATCH | `/boards/{boardId}/cards/{cardId}` | Змінити назву/опис картки | `200` |
| DELETE | `/boards/{boardId}/cards/{cardId}?version=0` | Видалити картку | `204` |
| POST | `/boards/{boardId}/cards/{cardId}/move` | Перемістити картку | `200` |

Створення дошки або картки: `{ "title": "Назва", "description": "Опис" }`; опис необов'язковий і за замовчуванням порожній. Створення колонки: `{ "title": "У роботі" }`.

Редагування: `{ "version": 0, "title": "Нова назва" }` або `{ "version": 0, "description": "" }`. Має бути хоча б одне змінюване поле. Для колонки дозволена лише зміна `title`.

Кожна вкладена сутність має належати дошці з URL. Відсутній, чужий або неправильно вкладений ресурс повертає однаковий `404 RESOURCE_NOT_FOUND`. Неавтентифікований запит спершу отримує `401`.

Колонка з картками не видаляється: `409 COLUMN_NOT_EMPTY`. Видалення дошки видаляє її вміст; UI перед цим просить підтвердження. Повторний DELETE вже видаленого ресурсу повертає `404`.

### Snapshot дошки

Відповідь на `GET /boards/{boardId}`:

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "title": "Наш Kanban",
  "description": "Розробка проєкту",
  "role": "OWNER",
  "version": 0,
  "createdAt": "2026-10-22T09:00:00Z",
  "updatedAt": "2026-10-22T09:00:00Z",
  "columns": [
    {
      "id": "22222222-2222-4222-8222-222222222222",
      "boardId": "11111111-1111-4111-8111-111111111111",
      "title": "Заплановано",
      "version": 0,
      "createdAt": "2026-10-22T09:00:00Z",
      "updatedAt": "2026-10-22T09:00:00Z",
      "cards": [
        {
          "id": "44444444-4444-4444-8444-444444444444",
          "boardId": "11111111-1111-4111-8111-111111111111",
          "columnId": "22222222-2222-4222-8222-222222222222",
          "title": "Узгодити API",
          "description": "Перевірити DTO разом із frontend",
          "version": 0,
          "createdAt": "2026-10-22T09:00:00Z",
          "updatedAt": "2026-10-22T09:00:00Z"
        }
      ]
    }
  ]
}
```

Порядок масивів є порядком відображення. Frontend не обчислює fractional rank і не сортує сутності за UUID або датою. Початкова межа core — 50 колонок і загалом 1000 карток на дошку; перевищення дає `409 BOARD_LIMIT_REACHED`. Ці запропоновані ліміти переглядаємо за вимірюваннями.

Сервер повертає узгоджений snapshot, а не суміш різних станів між кількома SQL-запитами; реалізація має забезпечити відповідну транзакційну ізоляцію читання.

### Пагінація дошок

```json
{
  "items": [],
  "page": 0,
  "size": 20,
  "totalElements": 0,
  "totalPages": 0
}
```

`page` починається з 0, `size` — 1–100. Значення поза межами повертають `400`, а сторінка поза кінцем списку — порожній `items` із актуальними total. Сортування: `updatedAt DESC, id ASC`. `Board.updatedAt` стосується її метаданих; активність карток поки не змінює порядок списку дошок. Offset-пагінація не гарантує незмінний набір між запитами під час конкурентних змін.

## 4. Переміщення та конфлікти

`version` стосується конкретної дошки, колонки або картки. Це не глобальна ревізія всього дерева. Зміна картки не потребує зміни version дошки чи колонки. Нові сутності отримують version 0; зміна власних даних або порядку збільшує version. Семантичний no-op може повернути незмінену version.

Перед зміною сервер перевіряє очікувану версію та виконує перевірку/запис атомарно. Якщо версія застаріла — `409 VERSION_CONFLICT`.

Для move передаємо **обох сусідів у бажаному кінцевому порядку**, вже без картки, яку переміщуємо:

```http
POST /api/v1/boards/11111111-1111-4111-8111-111111111111/cards/44444444-4444-4444-8444-444444444444/move
```

```json
{
  "version": 0,
  "targetColumnId": "33333333-3333-4333-8333-333333333333",
  "previousCardId": null,
  "nextCardId": null
}
```

Це переміщення до порожньої колонки. Інші випадки:

| Позиція | previousCardId | nextCardId |
|---|---|---|
| На початок | `null` | ID поточної першої картки |
| У середину | ID сусіда зверху | ID сусіда знизу |
| У кінець | ID поточної останньої картки | `null` |
| Порожня колонка | `null` | `null` |

Обидва поля обов'язкові навіть при `null`. Сусіди мають належати цільовій колонці й бути суміжними. Не можна вказувати саму переміщувану картку або однакові ненульові ID сусідів — це `400 INVALID_REQUEST`. Відсутній доступний target — `404`; сусіди або порядок, що вже змінилися, — `409 MOVE_CONFLICT`. Коли порушено кілька умов, після автентифікації та перевірки доступу спершу перевіряємо version, потім актуальний порядок.

Повертається оновлена `Card`, а не вся дошка. Для переміщення колонок аналогічний запит містить `version`, `previousColumnId`, `nextColumnId`.

Поведінка frontend:

1. Скасувати застаріле завантаження snapshot, зберегти попередній стан кешу та показати optimistic move.
2. Поки move цієї картки виконується, не надсилати для неї наступний move із тією самою version.
3. Після успіху прийняти актуальну version і повторно отримати snapshot дошки.
4. При відомій помилці відкотити optimistic move, оновити snapshot та показати пояснення.
5. При мережевому збої результат може бути невідомим: спершу звірити серверний стан, не надсилати POST автоматично повторно.

При одночасних optimistic-змінах rollback не повинен перезаписувати успішні зміни інших карток; для першої реалізації допустимо виконувати лише одну зміну порядку дошки за раз.

## 5. Формат помилок

Content-Type: `application/json`. Загальна помилка:

```json
{
  "status": 409,
  "error": "Conflict",
  "code": "VERSION_CONFLICT",
  "message": "Картка вже змінена. Оновіть дані та повторіть дію.",
  "timestamp": "2026-10-25T10:00:00Z"
}
```

Для помилок `@Valid` request body замість `message` повертаємо `errors` — об'єкт із одним повідомленням для кожного поля:

```json
{
  "status": 400,
  "error": "Validation Failed",
  "code": "VALIDATION_FAILED",
  "errors": { "email": "Некоректний формат email." },
  "timestamp": "2026-10-25T10:00:00Z"
}
```

Некоректний JSON, параметри запиту та перевищення байтового ліміту пароля повертають загальну помилку `400 INVALID_REQUEST`. Непередбачені винятки мають загальне повідомлення без внутрішніх подробиць.

| HTTP | code | Реакція frontend |
|---|---|---|
| 400 | `VALIDATION_FAILED`, `INVALID_REQUEST` | Показати помилки полів або запиту |
| 401 | `INVALID_CREDENTIALS` | Пояснити помилку входу |
| 401 | `ACCESS_TOKEN_MISSING`, `ACCESS_TOKEN_INVALID`, `ACCESS_TOKEN_EXPIRED` | Один refresh, потім один повтор запиту |
| 401 | `REFRESH_INVALID` | Очистити локальну сесію та запропонувати вхід |
| 403 | `CSRF_INVALID` | Отримати новий CSRF; не запускати нескінченні повтори |
| 403 | `ACCESS_DENIED` | Показати відсутність дозволу на операцію |
| 404 | `RESOURCE_NOT_FOUND` | Показати недоступність ресурсу |
| 409 | `EMAIL_ALREADY_EXISTS` | Помилка біля email у формі реєстрації |
| 409 | `VERSION_CONFLICT`, `MOVE_CONFLICT` | Оновити дані, пояснити конфлікт |
| 409 | `COLUMN_NOT_EMPTY`, `BOARD_LIMIT_REACHED` | Пояснити бізнес-обмеження |
| 429 | `RATE_LIMITED` | Врахувати `Retry-After` у секундах |
| 500 | `INTERNAL_ERROR` | Показати загальне повідомлення про збій |

UI спирається на `code`, а не на текст `message`; невідомий код або інша серверна помилка мають безпечне загальне відображення. `errors` можна показати біля відповідних полів форми. Формат стосується також майбутніх відповідей security filters. Клієнт обробляє й не-JSON відповіді проксі при інфраструктурному збої.

## 6. Як починаємо працювати

1. Разом переглянути endpoints, DTO й наведені правила. Зміни внести до реалізації відповідних задач.
2. Backend реалізує auth → дошки → колонки/картки → move, звіряючись зі специфікацією.
3. Frontend генерує TS-клієнт через orval і створює MSW handlers за цими DTO. Security-поведінку cookie додатково перевіряємо проти реального backend у браузері.
4. Першими інтегрувати login і list/create board; не чекати завершення всього backend.
5. До завершення A0 доповнити ER-діаграму й узгодити цей draft. Наявність файлів не означає завершення контрактної задачі в Plan.md.

Окремий WebSocket-контракт з'явиться на A3 у `docs/realtime.md`; поточний REST API працює без realtime.
